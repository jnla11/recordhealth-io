- GR-52. Defects to fix, no design change (a through e; GR-69 through GR-71 add design to the same build step):
  - a. The lock's refusal for a PHI fact with no token shows its own message on screen and names the facts by #N. It is never reported as "the log moved". Cause: `src/package-lock.mjs` answers the lock with 409 `package_lock_phi_untokenized`, its own message and the fact ids; the console's `adi-console/grading.mjs` reads every 409 other than `package_locked` and `package_lock_unvetted` as "The log moved", so the reviewer re-reads, clicks again, and never sees why the lock refused. This is the audit's headline: the document cannot reach lock.
  - b. The refusal for marking a per-user PHI type on a package with no signed-in user shows its own message. Never "the log moved". Cause: `src/package-append.mjs` answers 409 `phi_mint_subject_missing` with its own message; the same `adi-console/grading.mjs` collapse hides it behind "The log moved".
  - c. The PHI token line on the fact panel shows the fact's current token from the package's tokens layer, not the ingest-time value. Cause: `adi-console/app.js` builds the panel's Token line from the fact's core row, which carries the ingest-time token; the per-fact map the read serves in the tokens layer (`atom_token_uids`, built in `src/package-tokens.mjs`) is read in the console only for the reverse map, so a fact moved to a new token by an edit (OR-18 i) still shows the old one.
  - d. A PHI fact that already carries a token has its text edit back. The shipped rule stands: a value edit moves the fact to the token for its new value (PACKAGE_DESIGN OR-18 i). Cause: `adi-console/app.js` withholds the edit checkbox from any fact carrying a token, a hold written before §10 step 4 shipped and never lifted when it did.
  - e. The server's check that a field belongs to the fact's kind also applies to a reviewer-created fact, reading the kind from its creation. Cause: `src/package-amendments.mjs` resolves a fact's effective kind through the core index, and a created fact has no row there, so the check passes anything on a created fact (§9 item 15, resolved by this ruling).
  - GR-65. A reviewer-created fact named in a lock refusal is named by its first few words, for example new fact "Lisinopril 10 mg", never by an id fragment. A numbered fact stays #N. Sharpens a.
  - GR-66. The server's field-belongs-to-kind check reads a reviewer's kind correction addressed to a created fact's creation entry, the same way the lock does, so the two never disagree. Sharpens e. *Superseded in part by GR-78: the check this ruling sharpens no longer refuses the save; the fact needs attention.*
  - GR-67. A retired token shows on the PHI token line as no token. Sharpens c.
  - GR-68. The text edit is on for facts whose stored text contains a `{{PHI:...}}` placeholder; the edit box opens with the raw text. Known risk, recorded in §9 item 22: a reviewer could save placeholder text as ground truth. Sharpens d. *Superseded in part by GR-81: a fact whose text still holds placeholder text needs attention and blocks the lock.*
- GR-53. Word selection: whenever words are selected, the row shows two labeled actions side by side: "Move #N here" (only when a fact is selected) and "Create new fact" with a kind picker. The choice is never implied by whether a fact happens to be selected. Cause: `adi-console/app.js` renders one checkmark that re-points when a fact is selected and creates when none is, so the same click means two different things and a reviewer who meant to create moves the selected fact instead.
- GR-54. PHI mark: ticking PHI on a fact with no PHI type saves nothing until a type is picked; the mark and the type then save together as one change. Unticking saves on its own. Cause: `adi-console/app.js` commits the PHI checkbox on toggle like every other checkbox (GR-34), so the mark reaches the server with no type, no token is minted for it, and the type arrives as a second save; between the two the fact is a PHI fact with no token and the lock refuses it (§6.1).
- GR-55. Words the parser gave no box for: the selected line's words appear as a clickable strip, so every word on the line can be selected. No guessed boxes are drawn on the page image. The stored position is the words; what the page shows for them is the line's box the server already derives. Cause: `adi-console/app.js` draws one selectable rect per word that carries a box and skips the rest, so a word with no box cannot be selected at all and the fact on it cannot be created or moved.
- GR-56. Moving a created fact: the move rewrites the fact's creation, position and text together, so its text becomes the newly selected words. Undo one position save works on created facts the same as on ingested ones. Cause: a created fact's position rides its creation entry, and the word tool's move in `adi-console/app.js` writes pointer corrections on a core atom, so it had nothing to correct on a created fact (§9 item 14, resolved by this ruling). The carrier the move writes is GR-61 (§2).
- GR-57. Sections tab: Sections gets its own tab beside Grade Atoms. The Sections panel inside Grade Atoms is removed. In the Sections tab each section works as a fact does: a list row, select it, its box on the page, vet it (checkmark) or delete it (X), the Deleted group with Restore, change its kind and its parent. A reviewer can create a new section. The gesture for creating one (a section spans many lines and can span pages) is GR-59 (§7). The original need was to focus on one section at a time; how the Sections tab and Grade Atoms relate for that is GR-60 (§7). Finding: `adi-console/index.html` holds the Sections panel inside the Grade Atoms tab where GR-48 put it, and the owner has now stepped through it (GR-37); this ruling is the outcome GR-48's sharpening sprint waited for.
- GR-58. Tables: table and row authoring will live inside the Sections tab. Its design is its own session, not this pass. Recorded here as placement only; the table-row build step (§10 step 5, now step 12) points at that session.

**Owner rulings, fixed points (2026-09-26, the date rulings, after the GR-78 through GR-83 pass), superseding earlier sessions where they differ. Recorded in the owner's register. They are the outcome of the date audit GR-77 called for and settle §9 item 30. The design that carries them is `DATE_RULES_DESIGN.md`; §7 here points to it and restates nothing.**

- GR-84. One set of date rules, written once, used by the phone, the backend and the console. No side keeps its own copy of the rules.
- GR-85. The import keeps the vendor's normalized date instead of discarding it. If the vendor's reading and ours disagree, the fact needs attention (amber box).
- GR-86. Never invent precision. A date with only a year, or a month and year, stays that precise everywhere. No day or time is filled in.
- GR-87. A date that arrived as text (printed in a document or typed by a reviewer) is shown exactly as written. Behind it sits a normalized date, and every programmatic use (query, sort, longitudinal views, matching, scoring) reads the normalized date, never the text.
- GR-88. A date the system produces itself (not from text) displays in one consistent format everywhere.
- GR-89. The normalized date is the most precise machine form available, carrying only the precision the source has.
- GR-90. The normalized form is ISO 8601 with its partial forms: 2024, 2024-03, 2024-03-01, and 2024-03-01T14:30:00-08:00 (a date-time carries its time zone offset). Never padded to more precision than the source has.
- GR-91. The consistent display format is the long US form: March 1, 2024. Partial dates display as March 2024 or 2024. No ordinal suffix ("1st").

## 1. The reviewer's flow (replaces v1.2 §2)

1. Open a document, pick a package: the original core with the whole log folded in (§6.3).
2. Work the list, the Sections tab and the page image. Vet what is right (checkmark, GR-28). Fix what is wrong in the fact's detail panel (text, kind, section, PHI with its type as one change (GR-54), the fields that apply) and its position on the page image, through "Move #N here" (GR-53); a created fact moves the same way, its creation rewritten (GR-56). Create a missing fact by selecting words, picking a kind and pressing "Create new fact" (GR-53), and it joins the list as a fact like any other (GR-50). Words the parser gave no box for are reached through the selected line's word strip (GR-55). Sections are worked the same way in their own tab: vet, delete and restore, kind, parent, create (GR-57). Remove what is wrong (X); it drops to the Deleted group, restorable (GR-49). Each act is one append, saved on its own the moment it is made (GR-34), bumping the version and the package checksum (GR-39), painted from the re-read that follows, in-flight until then (GR-10), and a change attempted mid-flight is refused, not queued (GR-45).
3. Press "Mark reviewed": the lock (§6). To keep going, unlock; the next lock rebuilds.

Thumbs-up is the checkmark, thumbs-down is the X. "Accept N shown" is retired unbuilt.

## 4. Vetting, un-vetting and the fold (replaces v1.2 §6's buckets)

These are progress counts. They are not scores and nothing derives a score from them (§5). Per class C, folded to a position P (one fold rule, v1.2 §4): instances_C, every core instance minus synthesized atoms; rejected_C, whole-object head `rejected`; corrected_C, not rejected and any head `corrected`; accepted_C, neither and whole-object head `accepted`; unvetted_C, the rest; discoveries_C, live reviewer adds (not walker adds). The console and the lock header read these counts; the lock stores progress (§6.1).

**4.1 Un-vet, restore, and the fold (proposal).** Unchecking writes `remove` naming the accepted entry's `amendment_id`, no reasons: the reviewer withdraws their own entry. Restore (GR-49) is the same shape one verdict over: `remove` naming the reviewer's own `rejected` entry, and the object comes back unvetted, because the withdrawal leaves nothing on its key. The fold gains one pre-pass: collect the ids such removes name, skip those entries, then newest-wins. The atom's head falls back to whatever else is on its key (a correction stays; nothing, and it is unvetted again). Vetting never changes the build (§6.2), so the rebuild pays nothing for un-vet; a restore does change the build, by putting the object back in it. Validator: the named entry must be a live reviewer `accepted` or `rejected` in this log. Cost: the pre-pass in three folds (server, console, phone at sprint 9) under one shared fixture, one validator rule, `judged` reading the pre-passed fold. Rejected: a fourth verdict value, which breaks PACKAGE_DESIGN §6's fixed three.

## 6. The lock and the stored corrected package (GR-16; amends v1.2 §4 and §7)

**6.0 Per save, and at lock (GR-39).** Two things happen at two different moments and neither replaces the other. Every save appends one entry, bumps the amendment version and the package checksum: that is the save's whole visible effect, and it is what the re-read paints (GR-10). The totality step is the lock: the full rebuild from original plus log, stored once, under its own checksum (§6.1, §6.2). Re-affirmed after review 2026-09-18: a per-save version bump is not a per-save rebuild.

**6.1 What the lock writes.** One request. The server builds the corrected core (§6.2), writes it to R2 at `documents/{record_id}/{package_id}/corrected/{amendment_version}/core.json`, then appends `flag reviewed` with `provenance { progress, corrected_core_hash, rebuild_version }` in one transaction; a failed build appends nothing. `document_packages` gains `corrected_core_r2_key`, `corrected_core_hash`, `locked_at_version`; the versions ledger row gains `corrected_core_hash`. Every build is kept (R15); the original core never changes. The lock refuses, on screen, while any atom is unvetted, the control reporting the count (GR-17; "accept all remaining" is parked, §9); the count without the facts is a quiet path, §9 item 31 h. The lock also refuses while any fact shows amber, needing attention, naming each one, #N or new fact "<first words>" (GR-75, GR-76). An object in the Deleted group is not unvetted and does not hold the lock: its head is the reviewer's own `rejected` (GR-49). On a PHI fact with no token, the lock refuses (`package_lock_phi_untokenized`, shipped 2026-09-22); §10 step 4 and `F-NEW-SW` close with it (§9 item 6). The refusal is shown as its own message on screen, naming the facts by #N, never as "the log moved" (GR-52 a; the audit found the console collapsing it, §9 item 17). GR-54 keeps a fact from reaching this state through the panel at all: the mark and its type save together, so no reviewer mark leaves a PHI fact without a token.

**6.2 The rebuild rule.** Deterministic, pinned by a fixture beside the fold's. Fold to the lock; drop rejected atoms, relationships and rows, a restored object is not rejected at the fold and stays in (GR-49); apply every `corrected` head; add live reviewer discoveries as atoms, sections and rows with `origin: reviewer` and their log ids, a created fact's position and text read from the newest reviewer correction over its creation entry (GR-56, GR-61), a created section's box derived from the lines its creation names (GR-57, GR-59); apply relationship adds and removes; rewrite `section_id`, `parentId` and `table_cell_ref` from the entries that won, for `section_id` and `parentId` that means the relationship entries alone, since no other carrier is legal (GR-47); emit `row_in_table` and `table_in_section` from rows and cell refs; re-derive `source_region` and `source_text` for a re-pointed atom (GR-23), and for a moved created fact from its rewritten creation (GR-56); a position stored on words the parser gave no box for takes the line's box the server already derives (GR-55); drop nothing else. Sort atoms by `(page, line, word_start)`, unlocated last within their page; sections by first line; relationships by source. Vetting changes nothing here.

**6.3 Lock state and readers.** Lock state is the newest of `reviewed` and `unlocked` in the log. While locked, the write route refuses reviewer entries (`package_locked`, with an Unlock button), and every reader is served the corrected list alone (GR-17): its own hash, its own integrity checks, the original core withheld from the download though it stays stored on the server behind it, for history and comparison. Unlock appends `flag unlocked` and nothing else: the build stays stored, `corrected` is no longer served, export is withheld, readers get the original, alone, as before lock, until the next lock. The console never reads `corrected`: between saves it shows the original with the whole log folded in, re-read after every append, the rebuild's fold minus sorting and writing. Each atom shows its state from that fold: vetted, corrected (per field), deleted (in the Deleted group, GR-49), created (the "created" marker, GR-50), in a row, in-flight; a section shows the same states in the Sections tab (GR-57). A PHI fact's Token line reads the package's tokens layer as served with the read, never the core row's ingest-time value (GR-52 c). A header shows reviewer progress, never a score: "Locked at 1.n" or "Unlocked, N entries since".
