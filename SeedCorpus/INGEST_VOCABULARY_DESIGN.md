## 0. Verification of the audit's claims (all six confirmed, plus two facts the audit undersold)

The six unsafe sites all check out against the live codebase:

- **A1 — unknown job state throws.** `IngestPollDecision.forState`'s `default:` returns `.unknownState` (IngestPollDecision.swift:167-168); `LLMClient.pollAndFetchResult` converts that to a thrown `httpError(-1, …)` (LLMClient.swift:475-483, after emitting a drift event — the detection half already exists); the pipeline's generic catch sees a bookmarked record and parks `.awaitingServer(.pollLost)` (RecordIngestPipeline.swift:1337-1355). The record then renders "Reconnecting…" (IngestProgressPresentation.swift:73-74) on every reattach cycle until `IngestStallEvaluator.pollLostThreshold` (10 min of accumulated park) escalates to `.stalled` → "Taking too long — try again" (:130). Both claims are false: the server answered every poll.
- **A2 — blocked reason is discarded.** `IngestPollDecision.forState` passes `reason` through on `.blocked` (:150-153), but the `ingestBlocked` catch hardcodes `.needsAttention(cause: .subscriptionRequired, …)` (RecordIngestPipeline.swift:1274-1275; second site at :2435). Every blocked reason — including a future `blocked(vendor_unavailable)` park — renders "Subscription required" with an Upgrade button (IngestProgressPresentation.swift:118, :272).
- **A3 — arm terminal compared by string equality.** `status.arms?.parse.state == "done"` gates the OCR-complete and section-complete progress promotions (RecordIngestPipeline.swift:1175). A renamed arm terminal freezes the label ladder silently.
- **B1 — ArmStatus is brittle.** `ArmStatus.state` and `retryCount` are non-optional (IngestJobStatus.swift:31-33); one missing or retyped field inside `arms` throws the whole status decode and kills the poll. The `enqueued_at` String/Double incident is memorialized in the file itself (:69-74).
- **B2 — one malformed row kills the jobs list.** `IngestJobSummary` requires `jobId` and `state` (IngestJobSummary.swift:21-24) and the list decodes as one `[IngestJobSummary]`, so one bad row aborts `reconcileUnfetchedJobs` for that pass.
- **C — the six payload sites.** Unknown kind drops the atom (SegmentedAtomExtractionService.swift:167, :359); unknown column_role drops the atom (:206, :394); unknown edge kind drops the edge (:728); unknown phi_type on an `is_phi=true` atom persists it unflagged with a warning (:527-528); unknown `set_by` silently coerces to `.walker` (:735 — no log); unknown `classification_certainty` silently coerces to `.specific` (:260, :417 — no log, and note the coercion is *upward*, to the strongest claim).

Two facts the audit undersold, both load-bearing for this design:

1. **The safe pattern already exists in this codebase, four times.** `AtomSubtype` keeps unknowns as `.custom(raw)` with the raw string preserved verbatim (AtomSubtype.swift:220, :248-263). `RecordIngestPipeline.holdAttentionCause` allowlists exactly one reason string and routes everything else to the honest generic `.serverHold` (:511-514). `jobFinalIsCompletedWork` is "deliberately an exact single-class match: every other class — present or future — keeps the failure path, which is the safe side of this fork" (:526-531). `IngestRetryMode`'s code test is a denylist of client-minted codes so unknown server codes take the fresh-submit path. This design is a generalization of those four precedents, not an invention.
2. **Layer 2 is regenerable from Layer 1 (sacred rule 8), which is the structural asymmetry beneath "preserve vs drop."** A raw string preserved on Layer 1 can be reinterpreted by a *future app build's* `ContextLayerBuilder` — or a future dictionary entry (§5) — at the next Layer 2 rebuild; a dropped value cannot be reinterpreted by anything, because it no longer exists. (v2 note: with the dictionary ruling, "ship an app update" itself becomes "ship a dictionary entry" — the same asymmetry, one more rung down. See §5.) (v6, OR-13: the *economic* version of this argument — "preservation converts paid reingest into a free app update" — is retired from the present tense. Reingest is currently free and the corpus is dev data no one needs to keep; what preservation buys today is structural, not economic: three-way distinguishability, transparent-encoding promotion, and a floor proven correct while mistakes still cost nothing. The economics return at launch, when reingest means real users' documents and real vendor spend — and the floor must already be in place by then, because dev is the last time retrofitting it is free.)

## 1. The behavioral class model

The app treats every server-supplied lifecycle string as an instance of one of **three behavioral classes**. The classes are the closed set; the strings are open. Every switch over server vocabulary maps strings into classes; no code downstream of the classifier ever switches on a raw string.

| Class | Meaning to the user | Meaning to the recovery machinery |
|---|---|---|
| **PROCEED** | Nothing shown; the result arrives | Terminal and servable: fetch `/result`, persist, ack. Entered only on exact-match vocabulary (`complete`; `already_complete` on `/retry`) |
| **WAIT** | "We have your document; the server has it; no action is needed" — with sub-kind copy where an exact match earns it | Keep the `serverJobId` bookmark. Keep polling at the relaxed cadence (or park-and-reattach). Never fetch, never ack, never surface a failure, never offer retry. The stall ladder does NOT run against a server-confirmed wait — reachability-only polling (owner ruling 2026-08-08) already establishes that the server is the sole authority on whether a job is dead |
| **STOP** | The failure surface: honest cause where known, retry affordance where retry is meaningful | Terminal failure: route through `terminalFailureCause` / the manual-retry fork. Entered only on exact-match vocabulary (`failed` with no hold fields; a recognized refusal class) |

**The mapping rule, stated once:** exact-string tables admit a string into PROCEED, STOP, or a *specific* WAIT sub-kind. The `default:` of every classifier is generic WAIT. Unknown never resolves to STOP, never to PROCEED, and never to any copy that makes a claim the client did not observe.

WAIT has sub-kinds, because some waits earn more specific truth than others — but the sub-kinds differ only in copy and affordance, never in machinery (all of them keep the bookmark and keep polling or park-for-reattach):

- **wait/working** — exact matches: `created`, `submitting`, `running`, `assembling`. Progress labels, working cadence.
- **wait/queued** — exact match: `queued`. Queue-position copy, queued cadence.
- **wait/server-hold** — exact matches: `complete_partial` (partial repair), `running`+hold fields (dispatch hold), `failed`+hold fields with a non-user-actionable reason, `blocked` with a non-allowlisted reason. "Processing delayed… no action needed" meaning (the F-NEW-MV locked meaning).
- **wait/user-hold** — exact matches ONLY: `blocked`/held with reason `subscription_required` (→ upgrade affordance), the sign-in-required path. This is the only sub-kind permitted to render an action button, because a button is a *claim about the user* — that their money or their credentials are what is missing — and that claim may only be made on vocabulary the client positively recognizes. This is the direct fix for A2: `holdAttentionCause`'s existing allowlist shape becomes the rule for `blocked` too, and the two hardcoded `.subscriptionRequired` sites route through it.
- **wait/unknown** — the default. Everything else, including: an unrecognized job state, an unrecognized hold reason, an unrecognized blocked reason, a status body that fails to decode on an HTTP 200. Copy is the generic wait truth (§7). A drift event fires (§6). Machinery is identical to wait/server-hold. wait/unknown is unbounded on-device by design — see resolved OR-6, §10: the drift beacon is what makes a long-lived unknown visible, and it makes it visible to the *owner*, never as a user-facing wall-clock verdict.

**Why unknown = wait is correct and not merely cautious.** The client's only real observables are (a) reachability — a status body means the server answered — and (b) vocabulary it recognizes. An unknown string on a 200 proves the server is alive and holds the job; it proves nothing else. WAIT is the only class whose behavior is truthful under that evidence: it makes no claim, spends nothing, loses nothing, and self-heals the moment the server converges the job to a recognized terminal (the existing reattach/reconcile paths pick it up unchanged, exactly as `complete_partial` already does). STOP on unknown fails a user's document over our own ignorance; PROCEED on unknown fetches a result the server never said was servable.

**Arm vocabulary** gets the same treatment at smaller stakes. Arm states classify into **terminal-for-progress** (exact match: `done`) and **not-yet** (everything else, unknowns included). An unknown arm state means the fine-grained label ladder stays at its last honest rung — under-claiming progress — while job-level completion supersedes it regardless. First sight of an unknown arm state per poll run emits a drift event. The `== "done"` literal at RecordIngestPipeline.swift:1175 moves into the classifier so the string exists in exactly one place.

**Error-code vocabulary** (`error_codes`, `/retry` refusal classes, `documentUnprocessable` codes) is already conformant — denylist/single-match patterns where unknown takes the safe fork — and is adopted into this model unchanged. The conformance test for any future switch over server vocabulary: *name the class each arm maps to, and name which class the default lands in. If the default is not WAIT (for lifecycle) or preserve (for payload, §4), justify it in the code comment.*

## 2. Where classification happens, and what survives it

**One classifier per vocabulary, at the wire boundary, pure and testable.** This is already the codebase's shape — `IngestPollDecision` for job states, `holdAttentionCause` for hold reasons — and the design completes it rather than relocating it:

- `IngestPollDecision.forState` remains the sole authority on job-state classification. Its `default:` changes meaning: from `.unknownState` (throw → false pollLost) to a WAIT decision carrying the raw state. `.unknownState` as a concept is retired — deliberately reversing the "fail loud on unknown vocabulary" comment at IngestPollDecision.swift:58-60, because §6 makes it loud *to telemetry* instead of loud *at the user*.
- `holdAttentionCause` becomes the sole authority for *both* hold reasons and blocked reasons (the `blocked` path currently bypasses it at two sites). Its allowlist is the wait/user-hold gate.
- A small arm-state classifier sibling absorbs the `== "done"` literal.
- The payload enums classify at their existing decode sites in `SegmentedAtomExtractionService` (§4).

**The raw string survives classification. Explicitly:**

1. **Telemetry, always.** The classifier's unknown path emits the drift event (§6) carrying the verbatim raw string. This is non-negotiable: the raw string is the entire diagnostic content of a drift event.
2. **Diagnostic display.** The raw string is reachable from the diagnostics surface (the `IngestEventLog` export, and the NCC drift panel, §6). User-facing copy never interpolates it — an unknown server string shown to a user is jargon at best and a vendor name leak at worst.
3. **Persisted state, where the state machine already carries strings.** `AttentionCause.serverHold(kind: String?, reason: String?)` already persists raw server strings through `IngestState` — that precedent extends naturally: a wait/unknown park may carry the raw state the same way, so a later diagnosis can see *which* unknown state a record sat in without correlating timestamps against the ring. The carrier choice (associated value on the park vs event-log-only) is implementation detail; the constraint is that the raw string must be recorded at classification time at minimum in the event log. Note `IngestState`'s lenient decode (F-NEW-KO §H.1) absorbs any shape change here by construction — good posture on its own terms, though under OR-13 (v6) there is no legacy state anywhere that needs absorbing.
4. **Layer 1, for payload vocabulary** — the `.custom(raw)` pattern, §4. For payload enums, persistence of the raw string IS the fix, and (v2) is the substrate the future dictionary interprets — §5.

Downstream of the classifier, consumers (`IngestProgressPresentation`, the recovery coordinator, the stall evaluator, badge/queue surfaces) switch on class and cause enums only. The single-mapping rule the import-queue ruling established for status copy ("all three status surfaces render ONE mapping") already enforces this shape on the display side.

## 3. Decode tolerance policy

The principle: **strictness must be proportional to what the payload feeds.** A payload that feeds Layer 1 storage is load-bearing and fails loud. A payload that feeds classification and progress display must never be able to kill the machinery that would recover from its own malformation.

**`GET /v1/ingest/status/{id}` (`IngestJobStatus`) — nothing in it may throw.**

- `state` degrades to absent → classifies as wait/unknown. The job's identity came from the URL path; the poll needs nothing from the body to continue safely.
- `arms` / `ArmStatus`: every field becomes tolerant (`state` optional, `retryCount` defaulted). A malformed arm costs a progress label, not the poll. This is the generalization of the `enqueued_at` lesson — that fix repaired one field; this repairs the class of bug.
- `progress`, queue fields, hold fields, `createdAt`, `retryAt`: already optional; stay so.
- A body that fails decode *entirely* on an HTTP 200: classify as wait/unknown + drift event carrying the decode error (not the body — PHI posture, §6). The current behavior (throw → pollLost → "Reconnecting…") is the A1 lie again by another door.
- Non-2xx transport and genuine network failure keep their existing paths untouched — `.pollLost` remains correct when the server actually didn't answer; that is the one situation its copy is honest about.

**`GET /v1/ingest/jobs` (`IngestJobSummary`) — element-wise lossy decode.**

- The array decodes row-by-row; a row that fails to decode is dropped with a drift event, and the sweep proceeds over every row that decoded. One malformed row no longer aborts the entire recovery pass (B2).
- Within a row: `jobId` is the one load-bearing field — a row without an id is unusable for reattach, ack, or dismissal, and dropping it is the only option. `state` degrades to absent → the row classifies wait/unknown → the sweep skips it this pass rather than mis-acking it. `recordId` / `fetched` are already optional.
- **Named consequence (sacred rule 10 posture):** a persistently malformed row's job is never recovered by the sweep. It is not silent — the drift event fires on every sweep, a visible drumbeat — and it is not immortal: the liveness retention machinery (INGEST_LIVENESS_DESIGN §A) finalizes the job server-side on its own clock. The failure mode changes from "one bad row starves every record's recovery" to "one bad row starves its own record, loudly."

**`GET /v1/ingest/result/{id}` — stays strict at the envelope.** The result feeds Layer 1. A malformed envelope fails loud into the existing `failedDeterministic`/`missing_codex`-class handling, unchanged. *Within* a valid envelope, per-item tolerance is §4's business — item-level vocabulary drift must not fail the document, but envelope-level corruption must.

## 4. Result-payload policy — the six sites (RULED: preserve, everywhere)

**Owner ruling, 2026-08-15, absolute: PRESERVE at every payload site. Nothing is thrown away.** No per-site nil-degrade, no down-coercion, no silent coercion of any kind. Every unrecognized value survives on Layer 1 with its raw string intact. The v1 "acceptable cheaper variants" (degrade column_role to nil, down-coerce certainty to `.lowConfidence`, a bare `.unknown` for set_by) are all rejected — not on cost grounds but on structural ones: a degraded or coerced value is indistinguishable in storage from a genuinely-nil or genuinely-low value, which destroys exactly the information a later interpreter needs (§5). Preservation is uniform because reversibility must be uniform.

The governing asymmetry, from §0 fact 2, still frames why this is the right side of the trade — Layer 2 rebuilds from Layer 1; a dropped value is beyond every future interpreter's reach — with OR-13's re-grounding (v6): the argument is structural in the present tense, economic only at launch. Every site below emits a drift event (§6) on the unknown path — the two currently-silent coercions (set_by, certainty) become visible for the first time. (v5: OR-12 elevates this section's raw-on-atom rule from tolerance posture to one of three ruled storage roles — **the atom keeps its raw value verbatim, always**, whether or not a matching dictionary term exists. Nothing here changes mechanically; the app-side rungs 0–3 are untouched by OR-12.)

| # | Site | Today | Ruled behavior |
|---|---|---|---|
| 1 | Unknown atom `kind` | Whole atom dropped, logged | **Preserve as `AtomKind.custom(raw)`, atom persists whole on Layer 1, inert** (OR-1). Excluded by construction from Layer 2 — the builder skips kinds it doesn't understand, the quarantine pattern: no ContextAtom → no clinical surface, no AI context, no care graph. A future build (or dictionary entry, §5) that learns the kind picks it up at the next Layer 2 rebuild, no reingest |
| 2 | Unknown `column_role` | Whole atom dropped, logged | **`ColumnRole.custom(raw)`; the atom survives with the raw role intact** (OR-5). Consumers already handle nil roles; a custom role behaves as nil to every consumer that doesn't recognize it, but the string is there when one does |
| 3 | Unknown edge `kind` | Edge dropped, logged | **`EdgeKind.custom(raw)`** (OR-5). The `belongs_to_address` incident was this exact failure, already paid for once. Edges are inert typed pointers — storing an unconsumed one is free, and consumers resolve only kinds they know. This dissolves the "every new server edge kind requires an app build or the edge is dropped" coupling permanently |
| 4 | Unknown `phi_type` on `is_phi=true` | PHI flag not applied; atom persists unflagged; warning logged | **FAIL SAFE** (OR-2): preserve the raw type as `PHIType.custom(raw)` AND tokenize under the generic identifier namespace — `tokenType` for a custom type returns `.identifier`, riding the existing `.otherIdentifier → .identifier` machinery (PHIType.swift:67). No new derivation. Detail below |
| 5 | Unknown edge `set_by` | Silently coerced to `.walker`, no log | **`EdgeSource.custom(raw)`** (OR-5). The coercion was fake provenance (sacred rule 1) — the stored record asserted the on-device walker emitted an edge it never saw. Ends outright |
| 6 | Unknown `classification_certainty` | Silently coerced to `.specific`, no log | **Preserved-raw custom case** (OR-5). No down-coercion (rejected per the uniform ruling) and, above all, no upward coercion: consumers must treat any unrecognized certainty as *not* `.specific` — the weak side. **The *absent*-field default of `.specific` (`?? "specific"`) is dead (OR-16, v6): an absent certainty is drift.** Absence logs to the misfire log like any off-list value (as a distinguished absent marker under the certainty namespace, never a fabricated string), and the atom carries an explicit unknown — persisted *as absent*, so §5.2 property 2's three-way distinguishability (known / unknown-string / absent) survives in the encoding; what dies is only the silent promotion of absence to the strongest claim. Every consumer treats absent exactly as it treats an unrecognized certainty: the weak side. The v5 justification ("absence means an older server whose whole vocabulary was specific") was legacy reasoning with no legacy to serve — under OR-13, no old-server traffic exists to grandfather |

**OR-1, ruled: PRESERVE.** The v1 "against" arguments — `AtomKind` is the most load-bearing enum in the system, "present but inert" is a new state every consumer must handle, PHI interacts — were accurate, and they do not go away; they move. They are now the cost of rung 3 (§8) and the risk register (§9), not grounds to drop clinical data. The ruling's reasoning, re-grounded per OR-13 (v6): a dropped atom is beyond the reach of every future interpreter — no build, no dictionary entry, no Layer 2 rebuild can recover what was never stored — while a preserved one is picked up by the next build or dictionary entry that understands it, forever. (The economic form of this argument — paid reingest versus a free update — is launch-era; today reingest is free and the argument stands on structure alone.)

**OR-2, ruled: FAIL SAFE.** The server positively asserted "this span is PHI"; the client's response to not recognizing *which kind* must never be to treat it as *not PHI at all*. Ruled mechanics:

- The atom is flagged, and its value tokenizes reversibly under the generic identifier namespace: `PHIType.custom(raw)` with `tokenType == .identifier`. `phiTokenUid` derives normally via `PHITokenVault.uid(for:type:)` (sacred rule 6 machinery, untouched — the *namespace* is generic, the derivation is standard). Note what this rests on: `.custom` is a new `PHIType` case mapping to an **existing** `PHITokenType`, which is §5.1 case 1 — the permitted case. OR-2 does not mint a namespace and must never be implemented by minting one.
- This brings the atom under `IngestCompletionGate.phiInvariantHolds` (it is now tokenizable, so the gate covers it) and under chat anonymization (the vault knows the value, so the token pass replaces it outbound). The v1-named leak — server-asserted PHI passing through chat context untouched — closes.
- The raw `phi_type` string is preserved on the atom, so a later build or dictionary entry that learns the type can re-flag under the true type via the sanctioned `flagAsPHI` mutation. Cost acknowledged: until such a pass runs, the type label is wrong-but-conservative (a future `tattoo_description` tokenizes as a generic identifier), and tier-keyed UI shows it generically. See §9 item 2 for the token-namespace consequence.

**OR-5, ruled: PRESERVE, uniformly.** One pattern at all four remaining sites — the `AtomSubtype` pattern verbatim (custom case, known-string table, transparent single-string Codable, Equatable/Hashable over rawValue). The uniformity is itself the point: one mechanism to test, one encoding contract for the dictionary to rely on, no per-site bespoke degradation to reason about later.

## 5. The preservation floor beneath the server-owned dictionary

### 5.0 The root cause, named: the vocabulary is written down four times

*(v7: this inventory is superseded **as current state** by §11.6's copy ledger — the Postgres enum is gone with the v6 baseline, `vocabulary_terms` plus its snapshots is the surviving authority, and each remaining copy has a scheduled retirement phase. It is retained here in full as the historical frame the dictionary design answers.)*

**Owner reframing, 2026-08-15 (delivered with OR-7):** the vocabulary is currently written down three separate times — Swift enums in the app, validator lists in the Worker, and whatever ADI expects — three hand-synced copies with no mechanism keeping them honest. **That triplication is the root cause of every defect this doc addresses.** Recorded as such: A2's discarded blocked reason, the `belongs_to_address` edge that was dropped for months, the two silent coercions, the atom-kind drop, the `enqueued_at` type incident — every one of them is a divergence between two copies of a list that nothing forces to agree.

Verification against the live code sharpens the count to **four**, because the third copy is itself split, and the split halves fail differently:

| # | Copy | Where | Failure mode when it disagrees with the others |
|---|---|---|---|
| 1 | Swift enums | `AtomKind`, `AtomSubtype`, `ColumnRole`, `EdgeKind`, `EdgeSource`, `PHIType`, certainty | Atom or edge silently dropped / coerced at decode (§0 item C) |
| 2 | Worker pipeline validator lists | `pipeline-shared.mjs` — `VALID_PHI_TYPES` (:975), `SECTION_PASS_VALID_KINDS` (:1239), `PHI_ELIGIBLE_KINDS` (:965) | Value nulled server-side before the phone ever sees it (`phi_type` outside the set → null, :1168) |
| 3 | ADI route validator lists | `index.js` — `ALLOWED_COLUMN_ROLES` (:4479, five values), `ALLOWED_SECTION_KINDS` (:4557, fifteen values) | HTTP 400, whole submission rejected, nothing written |
| 4 | **The Postgres type system** | `data_atoms.entity_kind` is enum type `entity_kind_enum` — **33 values**, `baseline_001_adi.sql:11-45` | Insert throws *inside* the batched `adiSql.transaction(statements)` (index.js:4803) → **HTTP 500 `upload_failed`, whole document rolled back**, and the R2 PDF `put` that ran before the transaction is left orphaned |

Copy 4 is the one nobody counted, and it is the only copy that cannot be widened by editing a list. This is what makes OR-7's Worker-side scope concrete rather than hand-wavy (§9 item 1), and it is the strongest available argument for the dictionary: a fourth copy encoded in a database type is a copy no deployment process can keep honest. (v6, OR-14: a swapped extraction vendor is a *fifth* copy trying to be born — the new vendor's implicit output vocabulary — and the misfire log is what catches it: the changeover shows up as a drift wave attributed to the new extractor identity, §6.)

**The dictionary's job, stated in these terms:** collapse four copies to one authority plus derived views. Everything §5 specifies below is what has to be true of copy 1 for that collapse to be possible retroactively.

**v4 reconciliation — what the lookup table (OR-10) actually collapses.** The ruled vocabulary table (§8 rung 6) is copy 4's replacement and something more: it is the first copy that is *data* rather than code, which makes it the natural seed of the single authority the dictionary sprint needs — its identity scheme is therefore ruled now (§5.3) rather than left to that sprint. It also inverts the paragraph above: copy 4 goes from the only copy that *cannot* be widened by editing a list to the *easiest* copy to widen — a row insert. ### 5.1 The frozen core: PHI *vocabulary* is shared, PHI *derivation* is not

**Owner ruling OR-8, 2026-08-15:** the list of PHI types becomes shared, dynamic vocabulary like everything else. The token derivation algorithm does not. It stays frozen and byte-identical everywhere, permanently — because a changed derivation means the same person mints different tokens and their records stop linking.

**Where derivation actually runs — verified in code, 2026-08-15: the device, and only the device.**

- `PHITokenDerivation.uid(for:type:)` (PHITokenDerivation.swift:48-60) is the sole implementation: `uid = "{PHITokenType.prefix}_{first 12 hex of HMAC-SHA256(deviceSecret, "\(type.rawValue)\u{1F}\(normalize(value))")}"`. The secret is 32 random bytes in the Keychain under `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (:90-123) and is not a file, so it is excluded from every export and backup path by construction.
- The Worker **never derives**. It only *requires, stores, and reads* the uid: the ADI route rejects `is_phi=true` without a `phi_token_uid` (index.js:4485-4490) and inserts it verbatim (:4709); `ingest-do.mjs:2039` states outright that no `phi_token_uid` is minted server-side; `pipeline-shared.mjs:943` states the AI never proposes one. A repo-wide grep for HMAC, `token_uid` derivation, or any secret-keyed digest in `recordhealth-api/src` returns nothing.
- Consequence worth stating plainly, because it is the whole reason the freeze is enforceable: **the Worker cannot break derivation even if it wanted to.** It has no key material and no code path. The entire risk surface is the app binary and anything the app binary lets influence it.

**The invariant, stated explicitly:**

> **Vocabulary may grow. Derivation never changes.** Specifically: no value delivered by the dictionary — or by any other server-owned channel — may ever enter the HMAC message, the normalization, the digest length, or the uid format. The HMAC message today is exactly `PHITokenType.rawValue` + US separator + `PHITokenDerivation.normalize(value)`; every term in it except the document value itself is compiled into the app binary, and must stay that way.

This is the existing Sacred Rule #6 (`phi_token_uid` is derived infrastructure) and the existing CLAUDE.md rule that `PHITokenDerivation.normalize` must never be unified with the identity-matcher normalization, restated for a world where a server can push vocabulary. Neither rule anticipated a push channel; this clause is what carries them across.

**The hazard, named and bounded.** A dictionary entry *can* reach the derivation path, by exactly one route, and it is not obvious: the derivation is keyed on `PHITokenType`, but the AI/server-facing vocabulary is `PHIType`, and the two are bridged by a hand-written mapping — `PHIType.tokenType` (PHIType.swift:57-89), which routes e.g. `.memberNumber → .identifier`, `.licenseNumber/.deviceIdentifier/.otherIdentifier → .identifier`, `.facilityName → .org`. A dictionary that can express "PHI type X exists" is one schema field away from being able to express "…and it uses token namespace Y," and *that* field is HMAC input. Three sub-cases, ruled distinctly:

1. **Adding a `PHIType` that maps to an existing `PHITokenType` — PERMITTED to the dictionary.** Nothing that was ever derived changes; the new type simply starts deriving under an already-frozen namespace. This is the common case and the one the dictionary exists to serve.
2. **Re-mapping an *existing* `PHIType` to a different `PHITokenType` — FORBIDDEN outright, to the dictionary and to app builds alike.** Every value already tokenized under the old namespace re-derives to a different uid on next read; old and new records stop linking, and the vault's reverse cache holds the old mapping while new derivations mint the new one. There is no migration for this and none will be written (sacred rule 3 does not help here — the tokens are the linkage, not the data). If a mapping is ever judged wrong, it is a one-time owner-approved event with a stated reingest cost, never a routine edit. (v6, OR-13: while the corpus is dev data, that cost is ~zero — wipe and reingest corrects anything. The freeze discipline ships now regardless, because it only starts mattering on the day records exist that must keep linking, and that day is exactly when adding it becomes impossible.)
3. **Minting a *new* `PHITokenType` (new namespace, new prefix) — FORBIDDEN to the dictionary; permitted only as a compiled app-build change.** The namespace rawValue is HMAC input, so a pushed namespace is a pushed derivation. It is additionally sticky because of OR-2: any atom that fail-safe-tokenized as `.identifier` and is later re-typed into a brand-new namespace changes uid, which is §9 item 2's wart at larger scale.

**Structural enforcement, not convention.** The bound above is only real if the dictionary schema *cannot express* case 2 or 3 — the dictionary sprint must make token-namespace assignment a closed reference to a compiled-in enum case, resolved on-device, with an unrecognized namespace reference failing the entry rather than falling back to a raw string. A dictionary field typed as free-form String here is the whole hazard. This is the single hardest constraint this doc places on that sprint, and it is handed over deliberately: the floor can preserve a raw `phi_type` forever (§4 site 4), but it cannot preserve a token derived under a namespace that no longer means what it meant.

### 5.2 The floor's contract

**The larger ruling (2026-08-15):** atom vocabulary is to become **server-owned** — a dictionary such that new atom classes, subtypes, roles, and relationships become usable by a *deployed* app without an app release, and without breaking relationships between existing atoms. That is a separate architecture sprint with its own design pass. **This doc does not design the dictionary.** *[v7: superseded in exactly the declared sense — §11 is now that design pass, folded into this doc rather than shipped as a separate one. The floor/dictionary relationship stated in this section is unchanged, and the floor's seven properties still bind §11.]* This doc is the floor it stands on, and the relationship is stated here explicitly so neither effort drifts:

**The dictionary can only interpret what the floor preserved.** A dictionary entry shipped in 2027 is worthless against a document ingested in 2026 if the 2026 client dropped, coerced, or normalized the values the entry describes. Preservation is what makes the dictionary *retroactive*: it reaches back through every Layer 2 rebuild to data that was ingested before the dictionary — or the entry — existed. Every PRESERVE ruling in §4 is therefore not merely drift tolerance; it is the precondition for the dictionary being worth building. Conversely, the floor is complete without the dictionary: rungs 0–4 (§8) ship and stand on their own, and were justified on their own before the dictionary was ruled. (v6, OR-13: with a freely-reingestable dev corpus, retroactivity protects nothing *yet* — the reach-back argument is future-tense. The present-tense argument is proof: the floor is exercised and verified during dev precisely because dev is the last time a preservation mistake costs nothing to discover.)

**What "preserved" must mean structurally** for a later interpreter — dictionary-driven or plain app build — to actually use it. These seven properties are the floor's contract; an implementation that violates any of them has preserved a string but destroyed its usability:

1. **Verbatim and field-scoped.** The exact wire string, byte-for-byte — no trimming, case-folding, or normalization — stored in the same field position it arrived in (kind on kind, role on role). Normalizing is interpreting, and interpretation is what's being deferred; a "cleaned" string may no longer match the dictionary key the server later publishes.
2. **Three-way distinguishable.** In the persisted encoding, *unknown* must be distinguishable from *absent* and from *every known value*. This is the structural reason down-coercion and nil-degradation were rejected in §4: a certainty down-coerced to `.lowConfidence` or a role degraded to nil is permanently indistinguishable from a genuine one, and no interpreter can undo it.
3. **Transparent encoding — the actual reach-back mechanism.** A custom case must encode as the bare raw string (single-value container, `encode(rawValue)`) and decode as `known(raw) ?? .custom(raw)` — exactly the `AtomSubtype` Codable (AtomSubtype.swift:217-226). The consequence is that *promotion is automatic*: the moment a build (or dictionary entry) teaches the enum a string, every previously-custom occurrence on disk decodes directly into the known case on next read, zero migration, zero rewrite of Layer 1. A tagged or wrapped encoding (`{"custom": "foo"}`) would break this permanently. All five new custom cases (kind, column_role, edge kind, set_by, certainty) and `PHIType.custom` must use this encoding.
4. **The whole atom, not just the string.** A preserved unknown-kind atom carries every peer field exactly as a known atom would: server-minted `id`, `source_region`, char spans, `section_id`, `table_cell_ref`, `is_phi`/`phi_type` (via OR-2), `sourceText`, edges. An interpreter must find a complete atom, not a stub — provenance doctrine (sacred rule 1) applies to atoms we don't yet understand with exactly the same force.
5. **Identity and relationships stable.** Server-authoritative atom UUIDs persist as-sent (existing rule), and edges store target atom ids, never values. A `custom` edge between two atoms — either or both themselves custom-kind — resolves the day its kind is understood, because nothing about not-understanding it altered the identities it points at. This is the "without breaking relationships between existing atoms" half of the owner's dictionary requirement, delivered by the floor.
6. **Reinterpretation is rebuild, never patch.** Layer 2's builder *skips* what it doesn't understand and writes nothing back to Layer 1. Reinterpretation is always a full deterministic Layer 2 rebuild from Layer 1 (sacred rule 8) — never an in-place edit of stored atoms. The floor imposes exactly one interpreter contract: an interpreter reads Layer 1; it never mutates it. Sole sanctioned exception: PHI re-typing via the existing `flagAsPHI` carve-out (sacred rule 7), which is a classification flag, not a value.
7. **Inert means excluded loudly, everywhere.** Every consumer that excludes custom values — Layer 2 build, ADI/transit, metadata writeback, completion gate, chat context — names the exclusion (drift event or named-discard log), per sacred rule 10. "Present but invisible" is acceptable; "present, invisible, and unrecorded" is not.

What the floor deliberately does not decide: dictionary schema *[v7: decided — §11.1–11.2]*, delivery channel *[v7: decided — §11.3, §11.7]*, versioning *[v7: decided — §11.2]*, caching *[v7: decided — §11.2, §11.7]*, trust and authority boundaries *[v7: decided — OR-17]*, and whether/how the dictionary drives UI copy *[v7: deferred again, deliberately — §11.10]*. Resolved OR-4 (§10) folds the `state_class` idea into that sprint. A checklist of what the dictionary design pass must cover was handed to the owner alongside this revision. (v4: §5.3 now constrains one corner of that schema — term identity — by owner ruling; v5: OR-12 constrains a second — the dictionary's write path is human-only, and no extraction, ingest, or sync mechanism may ever author a term; everything else above stays that sprint's to design.)

### 5.3 Term identity is namespace plus code — the namespace-first frame (OR-11)

**Owner ruling OR-11, 2026-08-15: the vocabulary mechanism is namespace-first, with FHIR as one citizen rather than the frame.** FHIR terminology binding supplies the *pattern* — a coded value carries the system it came from, the code, and the original text (the `CodeableConcept` shape), and an "extensible" binding explicitly admits codes from outside the value set when none fits. That pattern applies universally here. FHIR's actual code systems apply only where a concept is genuinely clinical — and most of this app's vocabulary is not: job states, hold reasons, error codes, column roles, edge kinds, provenance (`set_by`), certainty, reliability tier, record categories, PHI types. Those get app-owned namespaces; PHI types in particular reference HIPAA identifiers, not FHIR. (Illustrative scheme, not final: `rh.atom.kind`, `rh.atom.subtype`, `rh.column-role`, `rh.edge.kind`, `rh.edge.source`, `rh.certainty`, `rh.phi.type`, `rh.job.state`, `rh.hold.reason`; external systems as their own namespaces: `loinc`, `snomedct`, `rxnorm`.)

Four invariants, recorded as decided:

1. **A term's identity is namespace plus code, never a bare string — and this lands from the start**, because retrofitting namespaces later is the expensive path. The vocabulary table (§8 rung 6) keys on `(namespace, code)` from its first migration. **This changes no wire contract and no Layer 1 encoding today:** a string arrives bare on the wire, but it is never bare in *identity*, because the field it arrives in assigns its namespace — which is precisely why floor property 1 (§5.2) requires field-scoped preservation. The table records explicitly what field position implies; future wire evolution may carry namespaces explicitly, but nothing here forces that now.
2. **The raw original text is preserved alongside the code, always** — the `CodeableConcept` precedent. This is already the floor's law at every §4 site and §5.2 property 1; it is restated here as *frame* rather than tolerance: preservation is not an error-handling posture, it is the permanent shape of a coded value in this system.
3. **A term may carry more than one code:** the app's internal code plus optional mappings to standard systems (LOINC, SNOMED CT, RxNorm). **Assessment, per the ruling's instruction — carrying the mapping from day one does *not* materially advance the ROADMAP cross-source matching work, and the columns should be carried anyway.** Verified against ROADMAP: the matching work (F-NEW-DR jigsaw clustering, F-NEW-O canonical code population, F-NEW-P FHIR-as-code-source, and F-NEW-OT's `kt_coding` capture — the LOINC/RxNorm/ICD-10 codes the pipeline already produces and the iOS decoder currently drops) all operates on codes attached to *individual atoms' values*: which analyte, which condition, which drug. A standard code on a vocabulary *term* (`rh.atom.kind`/`labValue` mapped to some LOINC concept) identifies a classification, not a clinical entity, and no clustering pass in ROADMAP consumes that. So: the mapping columns are cheap (nullable), correct under this frame, and should exist in the first schema — but populating them is not a workstream, and the real cross-source levers remain F-NEW-OT's atom-level capture and F-NEW-O/P's code table. §9 item 11 carries the conflation risk.
4. **User-defined vocabulary gets its own per-user namespace, never mixed with system vocabulary.** Future scope, not built here — but what is built here must not preclude it. Ruled shape: a reserved namespace prefix (e.g. `user.`) is set aside *now*, structurally refused by the shared table, so no system term can ever occupy it and no user term can ever land in the shared dictionary, the misfire log, or the drift beacon (v5: the review queue this clause named in v4 is deleted with OR-12's provisional mechanism; the misfire log inherits the exclusion). FHIR extensions are noted as too heavyweight for a consumer app; the lighter shape needs exactly five things: the reserved prefix; the same `(namespace, code)` identity and transparent encoding as every other term; storage in the user's encrypted per-user stores, never any shared table; structural exclusion from drift/anomaly egress and from NCC; and an outbound-tokenization ruling for user-authored term text (it is user content, PHI-adjacent) before any such term rides a chat payload. §9 item 10 carries the hazards.

## 6. The drift-reporting path (RULED: the server must learn — dedicated beacon)

**What exists:** detection is real but goes nowhere. Unknown-vocabulary sites log and/or emit `IngestDiagnosticEvent`s into `IngestEventLog` — a device-local, encrypted, 500-event ring whose only egress is a manual share-sheet export in Settings (SettingsView.swift:450). The owner ruled that unacceptable: a device-local ring requiring manual export does not satisfy "the server learns."

**Step one regardless — unify the event.** Drift currently rides generic kinds (`catchFired` at the unknownState site) or bare `print`s (the payload sites) or nothing (the two silent coercions). One event kind (`vocabularyDrift`) with a fixed shape: `{surface, field, rawValue, appVersion, extractor, count, firstSeenAt, lastSeenAt, exemplar jobId/atomId where the surface carries them}` — count/firstSeenAt/lastSeenAt are the v5/OR-12 amendment, so the misfire log can merge device-deduped events into honest first/last-seen rows with a pointer back to one real occurrence (the OR-12 block below); `extractor` is the v6/OR-14 amendment: the pipeline's extractor identity — vendor, model, version, as owner-defined strings matching the vendor naming of the liveness spend ledger (`ingest_spend_events`) — carried so a drift wave is attributable to the vendor that produced it, which is exactly the signature a vendor swap emits (lifecycle surfaces, where no extractor is in play, carry it null) — where `surface` names the classifier (jobState / holdReason / armState / atomKind / columnRole / edgeKind / edgeSetBy / phiType / certainty / decodeFailure) and `rawValue` is the verbatim unknown string. Deduplicated on device per `(surface, rawValue, appVersion, extractor)` with a count, so a 60s-cadence poll loop sitting on an unknown state for a weekend is one ring entry, not 2,880. PHI posture: a lifecycle-surface `rawValue` is server-minted vocabulary by construction; a payload-surface `rawValue` originates in the AI pipeline and gets the defensive treatment named in §9 item 6 before leaving the device. The decodeFailure case carries the decode error description only, never body bytes. This is the immediate-flush class of ring event (rare, high-value), matching the existing flush policy.

**Second event class (v3, OR-9): `vocabularyAnomaly`.** An oversized preserved string is not drift and must not ride the drift event — it gets its own kind, `{surface, field, valueLength, valueHash, jobId, atomId, appVersion, extractor}` (extractor per the v6/OR-14 amendment above), and **no `rawValue` field exists on it at all** (§9 items 4 and 9). The separation is the point: a drift row is a dictionary work item, an anomaly row is an upstream-breakage report, and one must never be triaged as the other. Both classes share the route, the NCC posture, and the observe-never-gate; they do not share a payload shape.

**OR-3, ruled: mechanism chosen — Option B, the dedicated fire-and-forget beacon.** `POST /v1/client-drift` (JWT-authed, the deduped event shape above), landing in the **misfire log** (v5 — the table OR-3 called "an NCC table" is named and shaped by the OR-12 block below) under the established posture — strict column allowlist, no free-form JSONB, waitUntil, **observe-never-gate** (a failed beacon send must be invisible to ingest; it can never block, delay, or fail anything). Surfaces as an NCC panel row: "app 1.4.2 saw jobState=`converging` ×41 across 3 users." **[v7, OR-19: the beacon's *build* is re-homed to Phase 4 (§11.7–11.8) — no `/v1/client-drift` route shipped with the misfire build, and the shipped table's `source` CHECK retains `'beacon'` awaiting it. The mechanism ruling in this block stands unchanged.]**

*Justification, weighing the four options now that this channel also serves the dictionary:* Option A (stay local) fails the ruling outright — the owner has said the server must learn. Option C (piggyback on existing calls) structurally misses the highest-value events — drift discovered on a job that never completes never rides a `/fetched` ack — and taxes two wire contracts that liveness and delivery own with a permanent observability rider. Option D (server-side version registry) is dissolved by the dictionary ruling itself: a hand-maintained registry of "vocabulary known per app version" is a throwaway draft of the dictionary's own bookkeeping, and it can never observe how the client actually *classified*, nor decode failures, nor payload-site drift. B is the only option that carries the client's real classification outcome across every surface — lifecycle, payload, and decode — including jobs that never complete; it is small and bounded (one Worker route, one allowlisted table, one client sender); and it is precisely the feedback loop the dictionary sprint needs: the ranked list of strings deployed clients are preserving-but-not-understanding *is the dictionary's work queue*, and the same feed verifies after a dictionary push that the drift it targeted actually stopped. The fleet is roughly one device today; the cost is being paid now because the channel's value begins exactly when the fleet stops being one device.

**v5 (OR-12) — the beacon and the misfire log are one mechanism, and the two v4 work queues are one observation surface.** OR-10's provisional review queue is deleted with the provisional insert. What replaces both it and OR-3's bare "NCC table" is the **misfire log** — the second of OR-12's three storage roles: an append-only observation surface, not a data store (the atom is) and not a queue of pending vocabulary (nothing in it is pending anything — promotion is the owner's deliberate act, §8 rung 6). Its purpose is tuning and recursive learning: the owner reads it to see what the extractor is actually emitting and why. Its shape is resolved here rather than left open:

- **Where it lives: server-side, in Neon, NCC-readable.** The stated purpose requires the owner to see *production* behavior — and ADI is DEBUG-only and superuser-gated, so a corpus-side-only log would see no production data at all, while a device-side-only log is exactly the manual-export ring OR-3 already ruled unacceptable. The device's `IngestEventLog` ring remains the local buffer (and the only place a gate-failed verbatim value survives anywhere off the atom); it is not a second log. (v6, OR-15 ratifies and hardens this: durable-in-Neon was never an interim phase and now explicitly lands **in the first build** — the table's DDL is first-build work, not "whichever rung ships first.")
- **Three sources, one table (v7, OR-18 — supersedes v5's "two feeders" and the beacon's "only production-facing detector" status).** The rung-4 beacon is the *transport* that fills the log from production clients, carrying both event classes; the rung-6 ADI route feeds it directly at dev-submission time; and the **ingest census** — `source='ingest'`, shipped 2026-08-21 (`recordhealth-api`: source CHECK widened 3272f76, `IngestDO.assemble()` repointed at the log ed0669e, reference sets 2a7e1e8) — files at DO assembly time. All extraction runs server-side in the DO, so the census sees **100% of extractor output** and is the **primary detector**; the beacon's mirror-population duty is NOT superseded, because the census structurally cannot see that population — only the extractor-output one. One NCC pattern across all three. Lifecycle-surface drift rows (unknown job states, hold reasons) land in the same table, distinguished by surface/namespace — they are the mirror population (server vocabulary the *app* didn't recognize, versus extractor output the *dictionary* doesn't hold), and splitting tables per population invites exactly the copy-divergence this doc exists to end.
- **Dedup — a row is an observation class, never one row per atom.** Rows collapse on **byte-exact value within a namespace, per extractor identity** (v6, OR-14: drift produced by vendor A and drift produced by vendor B must never merge — the log's stated purpose is seeing what *the extractor* is actually emitting, and a vendor swap is precisely the event that reads as a drift wave whose attribution matters). Field position assigns the namespace (§5.3 invariant 1 — the same string arriving in `column_role` and in `entity_kind` is two rows, deliberately, because cross-field co-occurrence is itself tuning signal). No case-folding, trimming, or normalization in the key: a normalized key merges strings the extractor actually emits distinctly, destroying the signal the log exists to capture (floor property 1, applied to observation). Each row carries: the value (verbatim or hash — next bullet), namespace/surface/field, occurrence count, first-seen and last-seen, and exemplar job + atom identity from the first occurrence. The device-side dedup key is `(surface, rawValue, appVersion, extractor)` (v6: extractor added, OR-14); the amended event shape (step one, above) is what lets the server merge honestly.
- **The PHI rule, stated once, governing both feeders and both event classes** (this is §9.6 applied to the log): a value is stored server-side **verbatim** only if it passes the pre-egress vocabulary-shape gate (single token, no whitespace runs, bounded charset — §9 item 6) *and* sits under the OR-9 length threshold. Anything failing either gate lands as the anomaly shape — **length + hash + identity, never the value** — while the verbatim value survives on-device: always on the atom itself (role 3), and in the ring. The same rule binds the ADI feeder even though a gate-failing value reaches Neon anyway *inside the atom row* (OR-7 ships atoms whole into the BAA-scoped corpus): the log never duplicates it, so the log stays a PHI-clean read surface regardless of feeder. A reviewer who needs the verbatim anomalous value follows the exemplar identity into the corpus row (dev) or the device ring (production). The residual §9 item 6 names — a vocabulary-*shaped* PHI fragment passes the gate by construction — is unchanged in kind, but the log gives it a longer-lived read surface; the gate specification tightens accordingly. One principle governs the gates' design (v6, OR-14): **no upstream vendor bound is ever load-bearing** — the gates are specified against *any* extractor's failure modes, never tuned to the observed behavior or advertised limits of the current vendor, because the vendor is swappable and the log outlives every vendor (§9 items 4 and 6).
- **The L7 seam (v6, OR-15) — separate tables, one pattern, correlation by id.** Base-level pathway logging is not this doc's to design and is not missing: INGEST_LIVENESS_DESIGN §4 already defines it as designed-but-unbuilt L7 scope — `ingest_phase_events` (full per-step detail, both environments), `ingest_spend_events` (per-attempt, per-vendor), four NCC panels, the failure taxonomy, and event-time alerting with ntfy push. The misfire log is **not an L7 table** and must not become one, for structural reasons: opposite write semantics (L7 is append-per-occurrence, naturally bounded per job; the misfire log is upsert-on-merge over observation classes), opposite PHI postures (L7's rule is ids/enums/counts/durations only, *no atom values*; the misfire log's whole purpose is a gated **verbatim value column**), and different feeders and lifecycle. What the two share: the one NCC pattern — strict column allowlist, no free-form JSONB, scrubbed, waitUntil, observe-never-gate — and the conventions: `environment`, `job_id`, and the extractor/vendor identity naming of the spend ledger, so a misfire row's exemplar joins against phase events ad hoc. **No foreign keys between the misfire log and any L7 table, in either direction**: correlation is by id only, so neither surface's absence or failure can gate the other. **The verbatim-column exception, stated once at the seam:** the misfire log is the *only* NCC table permitted a verbatim value column, admitted solely through the §9.6 shape gate and the OR-9 length threshold; no L7 table inherits that permission by analogy, and §9 item 9's erosion argument applies at table scale — the verbatim column must be structurally unreachable from every phase/spend/error writer, which is one more reason it lives in its own table.
- **Surface: a fifth NCC panel; alerting: anomaly only, via L7 (v6, OR-15).** The misfire log surfaces as its own panel alongside L7's four (ingest health, queue/concurrency, spend, holds & tombstones) — a curation *work-surface* the owner works through (OR-12's promotion loop), never rows folded into a health dashboard, with cross-links from a row's exemplar job id to that job's phase events and hold rows. When L7's alerting leg lands, the **`vocabularyAnomaly` write hook registers as an alert source** beside the hold/terminal hooks — an anomaly means the extraction pipeline is malfunctioning, exactly the class the 2026-08-06 liveness amendment moved into alerting scope, and the anomaly shape already satisfies the alert-payload allowlist by construction (OR-9 stripped the value from it). **Drift rows never alert**: a drift row is a work item, and the holds-panel philosophy governs — a durable row that stays visible until explicitly resolved, not a page. Until the alerting leg exists, anomaly rows are durable and NCC-visible, acceptable at dev scale (the owner is the only submitter; a broken extractor is discovered at the next dev submission regardless).
- **What bounds it: nothing yet.** Dedup bounds repeats, not unique values — the growth cost and the cap/retention policy (open, framed by OR-15) are §9 item 12.

**This also resolves OR-6** (§10): a record honestly parked on wait/unknown polls forever without a user-facing verdict, and the beacon is what bounds that in practice — a long-lived unknown becomes an owner-visible NCC row within one flush, and the escalation path is the owner shipping understanding (a build today, a dictionary entry tomorrow), never the user being handed a false "try again."

## 7. Honest copy for the WAIT class

The two current lies, named:

1. **"Reconnecting…"** (IngestProgressPresentation.swift:74) shown for a record parked `.pollLost` by an unknown state. There is no connection problem — every poll got an HTTP 200. The copy claims transport trouble the client never observed.
2. **"Taking too long — try again"** (:130) when the pollLost park accumulates past the 10-minute stall threshold. The server never called the job dead, the client never lost reachability, and the retry affordance invites the user to act on a job that needs nothing from them.

The copy rules, which are the class model restated for the display layer:

- **Copy claims only what was observed.** Connectivity claims ("Reconnecting…", "Waiting for connection…") require transport-level evidence — a request that actually failed. A 200 carrying unknown vocabulary is proof of reachability and must never wear connectivity copy. (`.pollLost` keeps its copy for genuine transport failure, which becomes the only path into it.)
- **A retry affordance is a claim that retrying helps.** It appears only on STOP-class states and on genuine bounded unreachability — never on any WAIT sub-kind. A server-confirmed-alive job with a Try Again button is the app arguing with its own evidence.
- **Cause claims require exact-match vocabulary.** "Subscription required" + Upgrade renders only from wait/user-hold (§1). Anything less certain gets the generic wait meaning.
- **The generic wait copy states the three things true of *every* WAIT sub-kind including wait/unknown:** we have your document; the server is working on or holding it; no action is needed from you. This is deliberately the same locked meaning as the breaker/hold copy in INGEST_LIVENESS_DESIGN §2 ("Processing delayed due to server issues. We will resolve and process your records shortly. No action is needed on your part.") — wait/unknown is, from the user's chair, indistinguishable from a server hold, and pretending to more specificity is how the current copy came to lie.
- **Exact strings are not this doc's to fix.** Per the standing pattern (liveness §2 ruling 4, and the placeholder-title comments already in `IngestProgressPresentation`), this doc locks *meanings*; final wording lands in the F-NEW-MV copy pass. The wait/unknown meaning slots into F-NEW-MV's existing inventory as one more row, not a new surface.

(v6, OR-13: with no users, the unmade decision loses urgency but gains a deadline — launch. It remains unmade.)

4. **Oversized preserved strings are never truncated — they are an anomaly, and clipping one would hide a broken extractor. — RULED (OR-9), reversing v2's recommendation.**

   **The ruling.** The v2 recommendation (cap preserved vocabulary at a few hundred bytes, store a truncation-marked prefix) is reversed. An oversized preserved string is **not vocabulary drift**. It is the extraction pipeline malfunctioning, and clipping it destroys the evidence of the malfunction while making the record look merely drifted. Ruled: **preserve the value whole**, and raise a loud anomaly to NCC as a **distinct event class from ordinary vocabulary drift** — a `vocabularyAnomaly`, not a `vocabularyDrift`, so it lands in its own bucket and is never triaged as "another string to add to the dictionary." A drift row says *teach me this word*; an anomaly row says *something upstream is broken*, and conflating them buries the second under the volume of the first.

   **The anomaly payload — and this is the whole point of the event's shape:** it carries **length, a hash of the value, and job plus atom identity**. It **never carries the value itself.** That is not a caveat bolted on; it is what makes the event safe to send at all.

   **This is deliberately also the resolution of item 6's PHI-egress concern for the oversized case.** An oversized payload string is the single most likely place for document text to end up — a model that misfires and spills a paragraph into a `phi_type` or `column_role` field produces exactly one signature, an implausibly long value in a vocabulary field. So the length trigger and the PHI trigger are the same trigger, and OR-9 resolves both with one mechanism: over the threshold, the value never leaves the device, only its length and digest do. Item 6 is narrowed accordingly to the *sub*-threshold case.

   **What preserving an unbounded string actually costs — verified in code, and there is no existing limit that would reject it first on the app side.**

   - *Storage, Layer 1.* `SegmentedFactStore` persists the whole per-record `[SegmentedFact]` array as one AES-GCM blob written atomically (`SegmentedFactStore.swift:256-257`). It is append-only but not append-*incremental*: every `save` / `saveBatch` re-encrypts and rewrites the entire file. A megabyte-scale string on one atom therefore taxes every subsequent write to that record, not just its own — the cost is O(file size) per append, and it is paid on the ingest hot path. This is the real storage cost, and it is worse than "one big row."
   - *Storage, Layer 2.* Free by construction: `ContextLayerBuilder` skips kinds it doesn't understand (§5 property 7), so an inert custom atom's oversized string is never copied into the ContextLayer.
   - *Transit.* `DocumentTransitService` builds the atom dictionary in memory and the string rides `entity_kind` / `column_role` / `phi_type` verbatim (:336, :352, :370). There is **no length guard anywhere in the app-side chain** — not in `SegmentedAtomExtractionService.build`, not in the store, not in the serializer. Confirmed by grep: the only `prefix(` calls in the extraction service are log-line truncations.
   - *Transit, server side.* The ADI route's only size gate is on the **decoded PDF** (`file_too_large`, 50MB, index.js:4611); the JSON body carrying the atoms is not size-checked. `stripNullBytes` (index.js:1454) walks every string but only removes NULs — it neither truncates nor rejects on length. The destination columns are all Postgres `text` (unbounded, 1GB), except `entity_kind` (today an enum — rejects on *validity*, not length; after rung 6 as amended by OR-12, an unbounded raw text column plus a nullable term reference — nothing server-side rejects on length, no string can mint a term because nothing mints terms, and the OR-9 gate's remaining job is keeping the oversized value out of the misfire log's verbatim column, §6). So nothing on the ADI path rejects it either.
   - *Upstream backstops, demoted to dated illustration (v6, OR-14).* The governing principle is now stated rather than inferred: **no upstream vendor bound is ever load-bearing** — every clamp, token limit, and response-shape guarantee is a property of the current vendor topology, not of the design, and the vendor is swappable. The 2026-08-15 verification illustrates why the principle was already the right conclusion: the Atom Pass response clamp (`DEFAULT_MAX_TOKENS = 16384`, pipeline-shared.mjs:39) bounds one arm's vocabulary strings at roughly 64KB by arithmetic (a value approaching it truncates the JSON and fails the shard as `truncated_response`), covers neither the LlamaExtract arm — a vendor adapter under no such clamp — nor a compromised or buggy server constructing the response directly. A partial backstop on one arm, none on the other, all of it valid only for one vendor topology that OR-14 says may change entirely. OR-9's anomaly, not trust in any upstream limit, is the answer under every topology.

   **Residual risk the ruling leaves:** the threshold is now a *detection* threshold rather than an *enforcement* one, so choosing it wrong is cheap in one direction and not the other. Too high and a genuinely broken extractor writes megabytes into an append-only encrypted store before anyone hears about it — and sacred rule 3's wipe-anything posture is the only remedy, since Layer 1 has no delete-one-atom operation (`deleteAtoms(forSourceDocument:)` is the finest granularity, and it is scoped to a whole document). Too low and the anomaly class becomes noisy and stops being read. There is no *storage* cliff to anchor it to, only the per-append rewrite cost above; pick it from what an honest vocabulary token can plausibly be (tens of bytes) with generous headroom, and treat the first anomaly as a bug report rather than a tuning signal. (v6, OR-13: the too-high failure's remedy — wipe-anything against a megabyte-fouled store — is currently trivial; like everything in this register, the pricing is for launch.)

5. **The upward-coercion bug can reincarnate through a lazy `default:` arm.** With certainty preserved as a custom case, every switch over certainty needs an arm for it — and nothing but discipline forces that arm onto the weak side. A future `default: return true` in a "is this atom confident?" check silently restores exactly the `.specific`-coercion this doc kills. The invariant to write into the code (and a test): *any default arm over a preserved-vocabulary enum must land on the conservative side for that consumer.* Swift's exhaustiveness helps only where switches avoid `default:`; prefer exhaustive switches with an explicit `.custom` arm. **Unchanged by v3.**

6. **The beacon's "PHI-free by construction" claim is weaker at the payload sites than at the lifecycle sites — narrowed by OR-9 to the sub-threshold case, and still the sharpest residual risk in the set.** Lifecycle rawValues (`jobState`, hold reasons) are server-minted vocabulary; safe, and they ship verbatim. Payload rawValues (`phi_type`, `column_role`, `set_by`, certainty, atom `kind`) originate in an AI pipeline, and a model that misfires can put document text in a type or role field. On-device preservation of that text is safe by the encryption invariant; *egress* to an NCC table is not, and vendor model behavior is not a construction guarantee.

   OR-9 resolves the **oversized** half outright: over the length threshold, nothing but length + hash + identity leaves the device (item 4). What remains is the **short** misfire — a stray surname, an MRN, a date fragment landing in a vocabulary field at a length no threshold would catch. That case is not covered by OR-9 and still needs the defensive treatment: a shape check before send (single token, no whitespace runs, bounded charset) and, on failure, send the hash instead of the value — the owner learns *that* and *where* drift occurred and can pull the verbatim string from the device ring if it matters. Note the shape check is now the *only* remaining guard for this class, since the length cap it was paired with in v2 no longer exists as a pre-send filter; it should be specified tightly rather than treated as a belt-and-braces afterthought. **v5 sharpening (OR-12):** the misfire log stores gate-passing values verbatim in Neon *by design and for reading* — the beacon's landing table is no longer telemetry the owner might inspect but a tuning surface the owner works in, so a vocabulary-shaped PHI fragment (a bare surname passes a single-token gate by construction) now gets a longer-lived, deliberately-read exposure. The residual is irreducible short of abandoning verbatim capture entirely, which would gut the log's purpose; the honest posture is a tightly-specified gate plus the §6 rule that a reviewer needing a suppressed value walks the exemplar identity back to the corpus row or the device ring. **v6 sharpening (OR-14, OR-13/OR-15):** two additions. The gate is specified **vendor-independently** — "vendor model behavior is not a construction guarantee" is promoted from caveat to rule: the gate is designed against *any* extractor's failure modes, never tuned to the observed behavior of the current one, because the log outlives every vendor (the §6 principle). And the exposure is priced for both eras: today the values at risk are dev/fake data (OR-13 — nominal exposure), but durable-first (OR-15) makes the log permanent and production-spanning, so the gate ships day one with the first-build table, not when real data arrives.

7. **The `entity_kind` guard, third form: from validation (enum) to registration (OR-10) to observation — and what the nullable reference gives up. — RE-RULED (OR-12), reversing the provisional-insert half of OR-10 this item priced; residuals stated.**

   **The ruling.** The extractor never writes to the dictionary. OR-10's provisional insert — the mechanism the v4 version of this item spent its length pricing — is rejected: the AI does not author vocabulary. Three storage roles replace it (curated dictionary; misfire log, §6; raw-on-atom, always), joined by a **nullable** foreign key: an unrecognized value is a null reference plus the preserved raw string. Promotion is a deliberate act — the owner reads the log, authors the term, runs the linking backfill (§8 rung 6) — never an arrival.

   **What OR-12 dissolves, each verified against the v4 text it replaces:** (a) *The flood — this item's headline v4 fear.* Nothing auto-enters the dictionary, so a broken extractor cannot dilute it; the dictionary is provably clean by construction. (The flood is displaced, not destroyed — it lands in the misfire log; item 12.) (b) *The status gap.* v4 discovered the ruled two statuses needed a third (`rejected`), and that FK references made rejected terms undeletable tombstones — the table was "in practice, append-only too." With no arrival path there is nothing to reject, and with human-only authorship nothing is provisional: **the status lifecycle is deleted entirely, and the dictionary is simply canonical terms.** (An optional `retired_at` for owner-authoring mistakes is curation metadata, not lifecycle — the undeletability of a referenced term is the one v4 observation that survives.) (c) *The OR-9 × OR-10 FK collision* — v4's "one genuinely unresolved mechanical point" — dissolves outright: an anomalous or oversized value is just another unrecognized value. Null reference, raw string preserved on the atom, hash-class entry in the misfire log. No sentinel term, no refusal, no rolled-back upload. The choice this item delegated to the `recordhealth-api` review is withdrawn; nullable-plus-raw-column *is* the answer, ruled.

   **What the nullable reference gives up — bluntly, because the lookup table was chosen partly *for* this.** OR-10's recorded surviving guard was: "referential integrity is **total** — every kind in `data_atoms` provably exists in the vocabulary table with a status; corpus `GROUP BY` joins a closed registry; nothing is ever unregistered." Under OR-12 that sentence is false in every clause. A null reference is unregistered *by design*; the misfire log is best-effort observation (observe-never-gated, deliberately permitted to fail without failing anything) rather than a constraint; and corpus queries join an open set. What structurally survives: the raw column is `NOT NULL` (no atom is ever kindless), a non-null reference is provably valid, and the dictionary is provably human-authored. The trade is coherent — it moves the corpus to the same posture as Layer 1 (preserve verbatim, interpret separately), which is arguably the posture this whole doc argues for — but it must be seen, not assumed away: every NCC panel or corpus query written against OR-10's closed-registry promise must instead treat the raw column as ground truth and the reference as enrichment, and the rung 6 reader audit now includes that reframing alongside the join-shape audit v4 named.

   **New carve-out this ruling requires, named.** Promotion linking is an `UPDATE` against `data_atoms`, which sacred rule 7 declares append-only. §8 rung 6 sanctions it on the `flagAsPHI` grounds — a term link is a classification flag, never the value — with `migrations/fneweh_entity_kind_backfill.sql` (owner-executed, 77-row kind rewrite) as exact precedent, and with the boundary that linking stays owner-initiated and batch: inline-at-ingest linking is the provisional insert by another name.

   **Unchanged from v3/v4, and worth keeping:** the beacon's coverage of `atomKind` drift remains the only *production* detector — ADI is DEBUG-only, so the misfire log's ADI feeder sees only dev submissions; production misfires arrive solely by beacon (§6) — which keeps rung 4 more load-bearing than its "independent, ship any time" placement suggests. **[v7, OR-18: re-priced. All extraction runs server-side in the DO, and the shipped ingest census sees 100% of extractor output — production *payload* misfires now arrive by census, not beacon. The beacon remains load-bearing for exactly the two populations the census cannot see: the mirror population (lifecycle-surface strings the deployed app couldn't classify) and, once Phase 4 delivers snapshots, version skew. Its build re-homes to Phase 4 per OR-19.]**

8. **NEW (from OR-8): the frozen-derivation invariant is currently enforced by nothing but this document.** §5.1 states that no dictionary-delivered value may enter the HMAC message, and bounds the hazard to the `PHIType → PHITokenType` bridge (PHIType.swift:57-89). But that bridge is a hand-written `switch` today, and the dictionary sprint has not been designed — so the constraint lives entirely in prose that a future schema decision could violate without anything failing. The ask handed to that sprint (a closed reference to a compiled-in enum case, unrecognized namespace references failing the entry rather than passing a raw string through) is the structural version, and until it exists the invariant is convention. Worth a `PHITokenSelfCheck`-style DEBUG assertion in the interim: the self-check already proves derivation is context-free and collision-free; extending it to pin the HMAC message construction against a frozen fixture would catch an accidental change to the message format, which is the failure nobody would notice until records stopped linking.

9. **NEW (from OR-9): a second event class on the drift channel needs its PHI rules stated once, not twice.** `vocabularyDrift` and `vocabularyAnomaly` now share one route, one NCC posture, and one flush policy, but have *different* payload rules — drift may carry a verbatim lifecycle rawValue; anomaly never carries a value at all. Two classes with divergent rules on one channel is how the stricter rule erodes: the obvious implementation shortcut is one sender with an optional `rawValue` column, and then the anomaly path is one bug away from populating it. The route's allowlisted columns should make the anomaly shape structurally unable to carry a value (separate columns, or a discriminated payload), which is why §8 rung 4 now says both classes must be designed together rather than the anomaly being amended in afterwards.

10. **NEW (from OR-11 invariant 4): the per-user namespace is a privacy boundary, not a naming convention — and the shared table must refuse it structurally from the first migration.** User-defined vocabulary is user content, PHI-adjacent by nature (a personal category like "Mom's dementia records" is itself sensitive). If a per-user term ever lands in the shared vocabulary table, it lands in a Neon table with an NCC review surface: a reviewer *seeing* it is content egress, and a reviewer canonicalizing it would launder a user's private term into system vocabulary. The reservation must therefore be structural now, while the table is being created — the shared table constraint-refuses the reserved `user.` prefix, and the misfire log and both beacon event classes exclude it (v5: the provisional-insert path this clause covered is deleted by OR-12; the exclusion moves to the log) — even though nothing user-defined is being built. The failure mode if this lands as convention instead of constraint: the first "sync my custom categories" feature request routes user terms through the path of least resistance — the shared table — and the boundary is gone before anyone rules on it. §5.3 invariant 4 names the five things the lighter-than-FHIR-extensions shape needs; this item exists so the *refusal* half ships with rung 6.

11. **NEW (from OR-11 invariant 3): the vocabulary table will be mistaken for the canonical-code table, and it is not one.** Two code-carrying structures now exist in the system's future: the vocabulary table (classifications — kinds, roles, types — with optional standard-system mapping columns) and the atom-level canonical-code work (F-NEW-O's `canonical_codes`, F-NEW-P's FHIR-as-code-source, F-NEW-DR's cross-source clustering, F-NEW-OT's currently-dropped `kt_coding`). They answer different questions — "what sort of thing is this atom" versus "which clinical entity is this value" — and only the second drives cross-source matching (§5.3 invariant 3's assessment). The organizational risk this item records: a future session, seeing LOINC columns on the vocabulary table, builds analyte matching against *terms* instead of *atoms* and produces a matcher that cannot distinguish glucose from potassium — both are just `labValue`. Cross-reference the two structures explicitly in whatever schema doc the dictionary sprint produces.

12. **NEW (from OR-12): the flood moved into the misfire log, and the log's growth is bounded by nothing that has been ruled.** Dedup (§6) collapses repeats: a poll loop sitting on one unknown state for a weekend is one row; a thousand atoms carrying the same unrecognized kind are one row. What dedup cannot bound is *unique* values — and the failure the log most wants to catch, an extractor spilling document text into vocabulary fields, is precisely the failure that emits near-unbounded unique strings. The OR-9/§9.6 gates route those to hash-class rows, which protects PHI but not row count: a hash-row per unique string is still a row per unique string, and a genuinely broken extractor can write thousands of rows per job. Neon storage is the small cost; the real one is **readability** — the log's entire purpose is that the owner reads it, and a flood makes it unreadable at exactly the moment it matters most, during the broken-extractor incident it exists to surface. Two operational decisions this creates that nothing has ruled: a **cap** (a per-job or per-device row budget with an overflow marker row — "+N further values suppressed, job X" — so volume stays visible when detail doesn't; sacred rule 10 satisfied by the marker), and a **retention policy** — still open, now framed by OR-15 (v6): durable-first casts the log as a long-term foundation, and OR-14 makes its history *more* valuable over time (it is the record of how each vendor drifted, across swaps), which leans the open decision toward **retain-with-disposition** — an acted-on marker rather than delete-when-done — over the v5 "discardable once acted on" framing. "Append-only" still means no in-place edits, not keep-forever, and the atom remains the raw value's home (role 3) either way. The retention decision should be taken **alongside L7's retention sweeper as one policy pass, not two conventions invented independently** (liveness §4's amendment already accepts a sweeper for phase-event detail rows); the cap decision remains this log's own, since unique-value floods are a problem phase events structurally cannot have. Both are numbers for the `recordhealth-api` review to set; this item exists so they are set deliberately rather than discovered at the first flood.

## 11. The dictionary: schema view, snapshot, delivery (v7)

### 11.1 The dictionary is what shipped

`vocabulary_terms` exists as of the v6 baseline (2026-08-21): keyed `(namespace, code)` per OR-11, retirement-marking (`retired_at` curation metadata per OR-12 — no status lifecycle), human-write-only per OR-12, 33 terms seeded under `rh.atom.kind` (31 live, 2 retired — `visitDate` and `reportDate`, owner-confirmed in bafe7ff), nullable `entity_kind_term_id` reference from `data_atoms`, `user.*` namespace refused by CHECK. v7 adds no second store. It adds the distribution layer that makes this table the source the other copies derive from.

Curation stays SQL-only (owner ruling, 2026-08-21): the one-tap promote-from-misfire-row control is deferred until a proper surface and consumer exist — it is designed with the ADI misfire panel (which rides the L7 build, §11.10), not before.

### 11.2 The snapshot

On every curation act the dictionary's version increments (monotonic integer) and the server generates an immutable snapshot: a compact document carrying version, namespaces, terms as (namespace, code, live/retired status, display, PHI default, multi-code mappings per OR-11's LOINC/SNOMED/RxNorm capacity), and per-surface closed/open declarations (provider subtypes stay open by construction). A version's content never changes; append-only at the version grain. All consumers read snapshots, never the table. The hot ingest path reads a per-isolate cached snapshot: zero database round trips per ingest.

### 11.3 The topology seam — ruled: Cloudflare KV (owner, 2026-08-21)

`vocabulary_terms` lives in the ADI group; the ingest DO binds only the user-flow group; the snapshot must live where all consumers reach. Ruled home: **Cloudflare KV** — versioned immutable blobs are its natural shape, cheap global reads, one new binding. Rejected alternatives, for the record: a snapshot table in the user-flow databases (all-Neon, but adds a cross-group write to the promotion loop) and an R2 object per version (same platform as ingest park, heavier read).

### 11.4 Consumers and what each retires

- DO ingest census: validates against the cached snapshot. The in-code sets in `ingest-vocab.mjs` demote to bootstrap-only fallback, marked as such. Retires the Worker pipeline copy.
- Extractor-facing definitions: tool schema enumerations and prompt vocabulary are generated from the snapshot at job time. Hard enforcement lives here and only here: closed fields become schema enumerations the extractor structurally cannot answer outside of. Retires the extractor-prompt copy. The queued standalone tool-schema fix is dissolved here (owner ruling, 2026-08-21): no interim fix against the in-code list ships and nothing repoints later — hard enforcement is built once, properly, in Phase 2, generated from the snapshot.
- ADI console: fetches the snapshot for kinds, subtypes, groupings. Retires the ADI route/console copy.
- iOS: §11.7. Retires the compiled-enum copy's gating role (the floor's `.custom(raw)` tolerance already made it survivable; delivery makes it derived).

### 11.5 Enforcement posture (two dials, unchanged and sharpened)

At the door: observe-never-gate stands everywhere it stands today. At the source: the extraction schema physically closes closed vocabularies. Absent certainty remains representable and remains drift (OR-16). The misfire log's before/after around the extractor-schema phase is the posture's measurement.

### 11.6 The copy ledger (supersedes §5.0's four-copy count as current state, keeps it as history)

Current copies and their scheduled retirement: (1) compiled Swift vocabulary, retired as gate by Phase 4; (2) Worker in-code sets, retired to bootstrap fallback by Phase 1; (3) ADI console lists, retired by Phase 3; (4) extractor prompt/schema vocabulary, retired by Phase 2; (5) `vocabulary_terms` plus snapshots, the surviving authority and its derived views. The Postgres enum type from §5.0's original count is already gone (v6 baseline).

### 11.7 Client delivery: open slots, fetch, buffer lane, beacon

One structural app release enables all of it; after that release, receiving new vocabulary correctly never requires an app update.

- Open slots: kinds and subtypes held as text against the cached snapshot. This is the floor's OR-1/OR-5 preservation pattern promoted from tolerance to design: `.custom(raw)` stops being an exception lane and becomes the ordinary state for any term the cached snapshot doesn't hold.
- Fetch: `GET /v1/vocabulary` with version negotiation (send held version, get not-modified or the new snapshot). Opportunistic refresh; never blocks ingest, display, or launch.
- Buffer lane: an atom whose term the cached snapshot lacks is stored losslessly and displayed generically. Nothing dropped, hidden, or blocked; behavioral classification still runs app-side per §2 and unknown still WAITs.
- Promotion on-device: a newer snapshot containing a buffered term moves those atoms out of the buffer automatically, audited per OR-20.
- Rich handling (typed parsing, native UI per kind) still ships in app releases; delivery makes receiving instant, not polish. Accepted platform constraint.
- Beacon: built here per OR-19, both populations live from day one.
- Frozen core: nothing in this section touches token derivation or token-namespace assignment (§5.1, OR-8, OR-17's standing exclusion).

### 11.8 Phasing (each phase shippable alone)

- Phase 1 (api): version counter, snapshot generation, snapshot home in KV (§11.3), `/v1/vocabulary` endpoint, DO census repointed to snapshot.
- Phase 2 (api): extractor tool schema and prompt vocabulary generated from snapshot; hard enforcement at the source; measured by the log.
- Phase 3 (api): ADI console reads the snapshot.
- Phase 4 (app, one structural release): open slots, fetch and cache, buffer lane, audited promotion, beacon. Last and largest.

Phases 2 and 3 are order-swappable.

### 11.9 Known warts carried (v7 observations, not v6 amendments)

- The shipped misfire dedup index omits `source`, so cross-source sightings of the same class merge under the first filer. Fix rides the next misfire migration; F-item until then.
- `extractor_version` carries the pipeline stamp until a real per-vendor version exists.
- ADI feeder rows carry a null extractor identity because that wire carries none.

### 11.10 Out of scope for v7

Misfire retention and caps (parked with L7's retention sweeper, §9 item 12); L7 itself (INGEST_LIVENESS_DESIGN §4 remains authority; the misfire NCC panel rides that build); per-user vocabulary in the reserved `user.*` namespace (boundary exists, feature undesigned); UI copy driven by the dictionary (deferred again, deliberately).
